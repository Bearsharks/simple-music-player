# 작업 워크플로

## 변경

- main 중심으로 개발하고 별도의 릴리즈 브랜치는 두지 않는다. 작업 브랜치 이름에 따라 CI를 차등 실행하지 않고 PR에서 검증하며, main 통합 후 다시 검증한다. PR 전 원격 검증이 필요하면 Draft PR을 사용한다.

1. 사용자 목표, 보존할 동작, 성공을 관찰할 실제 진입점을 정한다.
2. [구조](architecture.md)와 필요한 [정책](policies.md)을 읽고, 기능 인덱스에서 진입 코드와 소비자를 찾는다. 영향 분석의 범위와 한계를 확인한다.
3. 상태·경계·검증이 함께 설명되는 작은 변경 단위로 구현한다. 공유 계약이나 데이터 스키마가 불명확하면 먼저 결정한다.
4. 변경한 동작의 회귀 검사를 추가한다. 명령과 환경은 [package scripts](../../package.json), [도구](../../tools/), [Node 기준](../../.node-version)을 따른다.
5. 정상 경로뿐 아니라 실패·취소·재시도·늦은 응답·중복 동작을 검사한다. UI는 실제 앱에서 키보드·좁은 화면·레이어를 확인한다.
6. 구현과 검증 결과를 검토한 뒤 main에 통합한다. 미검증과 남은 결합은 완료 범위와 구분해 기록한다.

## 배포

- 검증 작업은 읽기 전용 토큰과 게시 작업과 분리된 실행 환경을 사용한다. 게시 작업만 쓰기 권한을 받으며, 같은 실행의 검증 완료 artifact를 식별자로 전달받아 재빌드 없이 게시한다.
- 자동 배포 커밋은 GitHub 공식 Actions 봇 신원으로 기록한다. 임의의 계정 이름으로 된 noreply 이메일을 만들지 않는다.
- [Release workflow](../../.github/workflows/release.yml)를 승인된 소스로 수동 실행한다. 게시하지 않는 실행으로 동일 절차를 검증할 수 있다.
- 배포는 소스 SHA, 고정 도구 체계, lockfile, 파일 해시로 식별한다. 재현성 검사와 브라우저 검증을 통과한 바이트만 게시한다.
- 게시 단계에서 재빌드하거나 같은 버전의 다른 바이트를 덮어쓰지 않는다. 현재 main·버전·Pages 설정·산출물이 다르면 중단한다.
- 앱만 바뀐 경우에는 게시된 확장 ZIP과 바이트가 같음을 확인한 뒤 기존 확장 릴리스를 재사용한다. 확장 갱신을 앱 변경의 필수 조건으로 만들지 않는다.
- 작업을 직렬화한다. 중간 실패는 성공으로 처리하지 않으며, 복구 시 동일 입력과 게시 상태를 확인한다. 태그 이동이나 자동 롤백으로 충돌을 숨기지 않는다.
- 운영 manifest·파일 해시·실제 진입 경로를 확인한 뒤 배포 완료로 보고한다. [배포 도구](../../tools/release.mjs)가 실행 계약을 소유한다.

## 기록

단위 테스트와 fixture는 외부 서비스·실제 오디오·물리 장치 검증을 대신하지 않는다. 결과와 제한, 배포 SHA·실행 링크는 [archive](../archive/README.md)에 남긴다. 상세 로그·파일 해시는 CI artifact와 운영 manifest를 원본으로 삼는다.
